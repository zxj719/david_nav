## 一、需要先澄清的一个口径：「速度环」是两套，不是一套

原报告把 David 的电机调校讲成一条线（STM32 PI Kp300/Ki800 + /odom 4.4→22Hz），
容易让人以为只有一层。实际上 David 的「速度/精度」治理是**上下两套独立标定**，
分别在两个时间点、用两种真值做的，建议在述职里分开讲，深度才立得住：

| | 层 | 时间 | 真值 | 解决的问题 | 落点 |
|---|---|---|---|---|---|
| 下层 | **STM32 电机速度环**（固件 PI） | 2026-05 | 示波/经验 | I 项 anti-windup 缺失 → 饱和后零命令滞留 → 命令时不动/跨次翻向 | Kp300/Ki800 |
| — | **ROS 驱动 /odom 频率 bug** | 2026-05 | — | 每 tick 只读 1 字节 → /odom 假性 4.4Hz；min_angular_z=0.20 把 DWB 微修正放大 5–8× | /odom 4.4→22Hz，跨次翻向 8/40→0 |
| 上层 | **位置环 position_controller**（ROS 侧 PD） | **2026-06-23** | **/odom 轮速 + slam_gt** | 换新底盘（大电机/大轮/宽轮距）后旧标定全部失配，需重表征 | 见下表，已落 `config/position_controller.yaml` |

原报告的 4.4→22Hz / 8/40→0 是**下层**（旧底盘驱动 bug）的成果，正确；但**上层位置环
在新底盘上的整组重标定（2026-06-23）原报告完全没有**，而那才是 6 月最硬的一组实测数据。

## 二、原报告缺失的关键一组数：2026-06-23 新底盘速度区间 + 位置环重标定

> 来源：`docs/reports/2026-06-23-new-chassis-retune.md`、`config/position_controller.yaml`、
> 实测 CSV `docs/reports/data_2026-06-23/`。方法 = 开环找死区/饱和（轮速真值）→ 闭环调位置环。
> 脚本**自写自跑自监控**（`scripts/chassis_characterize.py` + `scripts/pid_sweep.py`），
> 3×3m 场地、±1.05m 看门狗越界发零速、人守急停。

**一句话结论（值得写进述职，反直觉）**：换"更大电机+更大轮"后，底盘并不是"更有劲了"，
而是**宽轮距(50.5cm)+大轮+caster 让旋转阻力大增**——旋转命令必须**整体上抬 2~3 倍**才能起步，
直行死区也升约一倍。而且**位置环 PID 增益根本不用动，超调真正的旋钮是 `w_max` 和 `rotate_lead`**。
这条"先表征再下结论、别纸面推导"的纪律，直接推翻了我两天前"换了大电机就能把死区配方放宽"的乐观假设。

| 参数 | 旧值 | 新值（已落 yaml） | 依据 |
|---|---|---|---|
| `control_rate` | 50 | **20 Hz** | 新 wheeltec /odom 实测 20Hz，50 让 2/3 tick 拿陈旧 pose |
| `min_cmd_v`（直行死区） | 0.07 | **0.14** | 开环：0.10 1/3 卡死、0.12 仅 3cm/s 爬行、0.14 首个可靠推进 |
| `min_cmd_w`（旋转破缸） | 0.24 | **0.55** | 0.24 在新底盘**完全转不动**；持续破缸≈0.65 |
| `w_max` | 0.30 | **0.75** | 旋转极难起步，0.30 根本转不动；可靠≈0.80 |
| `v_max` | 0.18 | **0.20** | 开环**无力矩饱和**（大电机够劲），v_max 由控制+上肢稳定性定 |
| `rotate_lead` | 0.20 | **0.40 (~23°)** | w_max=0.75 停转滑行 ~20°，提前 ~23° 切零让 caster 动量补完 |
| `alpha_max` | 1.0 | **0.8** | 角加速柔化，降上肢扰动 + 降超调 |
| `dist.Kp/Kd`、`yaw.Kp/Kd` | 1.2/0.1、2.0/0.15 | **不变** | 闭环已达标，超调由 w_max/rotate_lead 主导而非增益 |

**±90° 旋转超调扫描（证明"w_max 主导超调"）**：w_max=0.70→~20°、0.90→~35°；rotate_lead 在 caster 噪声内差异小。

**全项验收实测（`validation_final.csv`，slam-gt 量级真值）**：

| 项 | 残余 | 超调 | 验收线 | |
|---|---|---|---|---|
| 直行 0.8m | −2.8cm（侧偏 +0.8cm） | 2.9cm | ~2cm | ✓ |
| 旋转 +90° | +0.35° | 19.0° | <1.15° | ✓ |
| 旋转 −90° | +0.68° | 22.4° | <1.15° | ✓ |
| pose（turn-drive-turn） | 位置 16.9cm，朝向 −3.28° | — | ≤20cm/20° | ✓ |
| 定点重复 ×3 散布 | 11.6 / 24.2 / 24.4cm（均值 ~20cm，σ~6cm） | — | — | caster 平面噪声天花板 |

**诚实归因**：定点重复 ~20cm 散布**不是增益问题**，是这台 caster 底盘"拖尾 + 终转 scrub"的
诚实精度上限；要更准只能**治本**（固件 break-away 前馈 / 换 caster）。这正好印证原报告"结构-控制-软件
乘法治理"的论点，且给了它一个量化的天花板。

**一个值得讲的控制理论判断（深度加分项）**：位置环结构刻意定为 **PD（`Ki=0`）**，不是 PID。
理由：plant 是"速度入/位置出 = 自带积分器(type-1)"，纯 P 即给零稳态误差；加 I 会
①升 type-2 过冲、②**死区 + I = 极限环**（误差小→P 出力低于死区 floor→不动→I 积起→破缸 lurch→过冲→反号 hunting），
③主误差是 caster 随机散布、I 只能修恒定偏置修不了随机噪声。（见
`docs/superpowers/specs/2026-06-23-chassis-param-determination-via-slamgt-design.md` §6）

## 三、对原报告 §2.6「自动调参流水线」的重大更新：真值源已从 AprilTag 转向 slam_gt

原报告 §2.6 写的真值 oracle 是「车载相机 + 场地 AprilTag 群 + 多标签联合 PnP」。
**这个口径已经过时**——经过 2026-06-17 对 AprilTag 方案的可行性评估，最新（2026-06-22/23）
**改用更省、已经在跑的 slam_gt 作位置真值**。建议述职里更新成下面这版，更扎实：

**新口径：按"谁擅长"分配真值（双真值源）**

| 真值源 | 量什么 | 为什么 | 用在 |
|---|---|---|---|
| `/odom` `twist`（轮速计） | **速度** | 轮速是本地瞬时量，不积分→不漂 | 开环死区/饱和（Phase A） |
| slam_gt `/groundtruth/pose`（slam_toolbox 锁图 map 帧） | **绝对位置/朝向** | /odom **位置**漂移巨大（实测一轮旋转漂 >2m），不可信 | 位置精度 + 导航测试（Phase B/C） |
| `/scan` | 障碍距离 | 真值丢失兜底；忽略本体臂 ~0.74m 自回波 | 全程安全 |

**为什么这是个进步而不只是换工具**：AprilTag 路线（2026-06-17 评估）能算 tag→camera，
但**算不出 robot→world**（真正要的真值），且交付的 `apriltag_pose.py` 有一个致命**死代码 bug**
（`--no-undistort` 用 `action="store_true", default=True` → 永远 True，鱼眼去畸变从没生效，
solvePnP 吃原始畸变图 → 边缘系统性偏差）。我修了 3 个 bug（去畸变开关、tag-size 0.28m 推导、
live 模式分辨率陷阱），评估出"自标定(开机自转一圈)+ 多标签联合解"能到 **cm 级位置 / 1–2° yaw**，
够 A→B 调参但够不到动捕绝对精度。**而 slam_gt 已经在跑、锁图即真值、无需贴标定板，直接更优**，
所以把真值源切过去，AprilTag 留作未来融合项。

**Phase A 已经是"实测完成"而非"待实车"**（原报告把整条流水线标成"硬件步骤待实车"，偏保守）：
- Phase A（开环速度区间）**2026-06-23 已在实车跑完**，结果已落 yaml（见 §二）。脚本：`chassis_characterize.py`(480 行)。
- Phase B（位置环 PID 闭环重验）：`pid_sweep.py`(192 行) + 给 `position_controller_field_test.py` 加 `--groundtruth` 增量，进行中。
- Phase C（真值下的导航测试）：`nav_trial_runner.py` 已设计未写（固定 map 回路、量真值精度 + 避障余量）。

## 四、原报告未覆盖的导航工作（均在本 workspace 有据可查，建议增补）

### 4.1 底盘差分几何变更 —— 旋转中心解耦（2026-06-22）
> `docs/reports/2026-06-22-wheels-forward-rotation-center-update.md`，commit `8b402e4`

不只是"两轮前移 16.5cm / 轮距 50.5cm"。关键认知是：**双轮前移后旋转中心不再与 base_link 重合**，
nav2 整栈用 `base_footprint` 作 `robot_base_frame` 且就是旋转中心，所以 base_footprint 必须一起
前移到 X=+0.165 才能让"nav2 绕 robot_base_frame 原地转"在物理上成立；同时换 22cm 大轮 → 机身抬高
15.75cm → base_footprint z 由 `轴心 z − 轮半径` 推到 −0.4075（顺带让激光滤地高度假设重新成立）；
nav2 footprint 多边形（local+global 两处）随之 X 后退 0.165，inscribed 0.30→0.255。**做了"单一真值源"
解耦**：差分几何集中进 URDF 顶部注释块（`wheel_x_offset`/`half_track`/`wheel_z` + 推导公式），
下次改底盘尽量只改 URDF。这是一次"结构层"改动里把几何一致性做扎实的典型。

### 4.2 与抓取栈 TF 统一 + 坐标点导航协议 v2（2026-06-11/12）
> `docs/reports/2026-06-11-waypoint-nav-v2-integration-and-tf-unify.md`、`base-to-base_link-tf-说明.md`，
> commits `b1f421e` `7b96308` `77fa381`

- **根因**：抓取(机械臂)栈的 RSP 发 `world→base_link`，导航 chassis RSP 也发 → **base_link 双父 →
  TF 树分裂 → ConnectivityException → 导航执行器失败 + MoveIt 关节校验失败 → 机械臂轨迹 abort(−4) 瘫痪**。
- **修法**：`base→world→base_link` 两段**零变换 identity 桥**（兼容新旧两版抓取栈）；导航 RSP 改名
  `nav_robot_state_publisher` 且 `robot_description` 重映射到 `/nav/robot_description`，不再被抓取 URDF 覆盖；
  pre-flight 清理从"无差别 pkill RSP"改成**选择性清理**（只删残留 chassis RSP / 旧式 base→base_link 静态 tf，
  保留机械臂 RSP/相机 tf）。**约定**：base_link 父帧只由导航发布。这是一次跨子系统（导航↔抓取）的接口治理。
- **协议 v2**：`navigate_to(target_id:string)`（查 POI 表）→ `navigate_to(target_pose{x,y,theta})`（直接收坐标），
  保留 v1 回退；配 headless 一键脚本 `start_waypoint_nav_headless.sh`。

### 4.3 膨胀感知"双阈值"路径稀疏化（2026-06-11，设计稿）
> `docs/reports/2026-06-11-inflation-aware-sparsifier-design.md`，commit `db9460a`

原报告说稀疏化是"Bresenham 直线视距 + 保留机器人半径余量"。补充其设计深度：现稀疏化用
LOS≥99 只挡 inscribed，**直线段会穿膨胀梯度带**，叠加机体 0.84×0.60 + 控制误差（caster 超调 0.2–0.4m +
定位漂移 ~0.85m）能让机体侵入墙体 0.8m。设计了**双阈值 LOS**（strict 50 优先走干净走廊 / fallback 99
窄道不瘫痪 graceful degrade）+ 膨胀带加宽（`inflation_radius` 0.40→0.75、`cost_scaling` 1.5→2.5）+
终段豁免（终点天然在膨胀里）。**诚实标注**：此为设计稿，前置依赖未解（/scan 被同网 om1 设备劫持、
定位动态漂移 ~0.85m）才有意义，**未实现**。

### 4.4 底盘驱动跑中崩溃的"三件软件兜底"（2026-05-23）
> `docs/reports/2026-05-23-chassis-driver-death-mid-run.md`，commit `e2b17b4`

一次 19 分钟实跑中 `wheeltec_robot_node` 因 `serial::IOException(5)` 崩溃，暴露三个系统性缺口：
STM32 **无 cmd_vel 看门狗**（崩溃后死保最后一帧 v=+0.5 不停）、脚本无底盘存活监控（**死了 45 秒 nav2 才发现**）、
separator 无 odom 失活上报（日志 38 秒 `act` 不变却显示正常值）。我落了**三件软件兜底**（STM32 看门狗
归固件队列）：①脚本 5s `kill -0` 存活监控 + SIGUSR1 触发**自动重启一次**；②separator 加 `odom_stale_sec=1.0`
失活 WARN + 强制零速；③关机前先 `pub --once /cmd_vel 0` 0.6s 再 SIGTERM。把"失控盲区"从 45s 压到 <5s。
这条很适合放进述职的"交付/安全意识"。

### 4.5 6.23 demo：务实兜底路线（死序列 + 重复-goal 倒车直冲）
> `david_nav/david_nav/dead_reckoning_executor.py`(319 行,新增,未提交)、
> `docs/superpowers/specs/2026-06-23-repeat-goal-reverse-and-blind-direct-design.md`，commits `2326862` `17ca191` `e59f5fe`

为赶 6.23 抓取 demo，做了一条**绕过 nav2 的务实兜底**，体现"demo 必须先能跑"的交付权衡：
- **`dead_reckoning_executor`**：收到任意 `NavigateToPose` goal **丢掉 target_pose**，只看 /odom 轮速跑固定开环序列
  （后退 1m → 原地转 π/2 → 前进，默认关），不依赖 nav2/planner/map/TF。`start_waypoint_nav_headless.sh`
  **当前默认就是这个 action**（不起 planner/waypoint_follower/position_controller），WebSocket 协议对 server 完全不变。

**诚实标注**：这是 demo 兜底/开环，不是最终架构；位置精度明显低于规划路线，靠后续抓取流程精对。
但它真实地让 6.23 demo 跑起来了——这点应进述职而非藏起来。
