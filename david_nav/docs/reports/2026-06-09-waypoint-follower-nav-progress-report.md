## 0. 工程全景：一个物理根因，三层治理（结构 / 控制 / 导航软件）

David 是 **70kg 量级重载差速底盘 + 被动万向轮 + 小电机 + 纯 P 电机环**。这套硬件的
物理特性 —— 大静摩擦、力矩受限、万向轮拖尾与横向静摩擦、纯 P 无法消稳态 —— 是一切
循迹/定点精度问题的**共同根因**：低速 stick-slip、起步死锁、旋转后给小线速度卡死
caster、停车按动量过冲。针对它，工程上分三层推进，**越底层越治本**：

### ① 结构层（治本，改物理）
- **已做**：换**更大电机 + 更大轮径** —— 提升可用力矩、抬高破启能力；同时修正了
  轮速计标定（原值偏小约 3×，曾导致里程计/速度严重失真）。
- **待做**：改为**菱形轮系布局**以降低底盘的**非静定（过约束）度** —— 现布局下被动
  万向轮与驱动轮互相"打架"产生拖尾/横向摩擦；菱形分布（驱动轮置于横向中线、万向轮
  前后对称）减少冗余约束，从根上削弱 caster 拖尾与转向阻滞。

### ② 控制层（电机速度环，治标偏本）
- **已做**：改 **STM32 固件** + 整定速度环 **PI**（最终 Kp300 / Ki800，从 1200 退回）。
- **待做**：**破启前馈（feedforward）** —— 按需求量给一个克服静摩擦/万向轮破启的前馈
  脉冲，是 cm/mrad 级精度的关键"治本"手段，目前尚未做。

### ③ 导航软件层（本报告主体，叠在上述之上）
位置环（精确点到点）+ 航点跟随（Nav2 规划 → 稀疏化 → 逐段驱动）是最上层，用软件策略
（速度死区地板、caster-safe turn–drive–turn、预测性刹车等）去**适配尚未治本的底盘**。
它能达到的精度上限，最终由结构层与控制层决定 —— **结构越接近静定、前馈越到位，
软件层就能越简单、越准**。

> 优先级：结构（菱形轮系）与控制（前馈）是降低软件补偿负担的治本方向；导航软件层
> 功能已就绪（见下文），实车精度需与底层改造**同步迭代**，而非靠软件无限堆补偿。

## 1. 目标一句话

把 **Nav2 当成纯全局规划器**，把它生成的路径稀疏化成若干「相邻两点之间无障碍、
且距离 ≤ 3m」的航点（waypoint），再由已有的 **位置环（position_controller）逐段精确
驱动**。每段都是验证过的无障碍直线，所以位置环盲走直线是安全的 —— 这正是两个航点
约束存在的意义。等价于：**Nav2 只规划，原来的局部控制器（DWB）被位置环替换**。

## 2. 整体架构（概念层）

```
RViz 发目标(map)
   → Nav2 planner 出一条全局路径（绕开障碍）
   → 稀疏化：相邻航点直线无障碍 + ≤3m
   → 位置环逐段 turn-drive-turn 驱动
   → 底盘
```

- **保留**：Nav2 全局规划 + 全局 costmap（出路径、做通视校验）。
- **旁路**：Nav2 局部控制器 DWB 及其下游平滑/适配链；位置环输出经自带的优先级
  仲裁直接进底盘，是该链路上唯一的速度来源。
- **静态地图假设**：航点在规划时一次性校验，运行中不做动态障碍监控与重规划。

- **已验证（离线/无硬件）**：纯逻辑单测全过；整栈节点都能起来；各接口/话题/可视化
  齐全；目标点击能触发；启动与配置无报错。

## 4. 当前阻塞问题：机器人被定位在地图原点（定位/TF 层，非本特性 bug）

实车首次联调发现：**规划出来的路径不是从机器人当前位置出发，而是从地图原点出发。**

### 诊断结论（已用最近一次运行日志定量复核）

- 两次下发目标（间隔约 26 秒、其间底盘里程计明显移动），反解出机器人在 **map 坐标系
  里的位姿都精确停在地图原点**，而底盘 `/odom` 里程计位姿却在变化。
- 日志中规划器持续报 **「Robot is out of bounds of the costmap」**（机器人落在地图范围外）。
- 核对接口语义确认：规划起点取的就是机器人本体坐标（`base_footprint`），配置正确；
  规划器和本节点读的是**同一个** `map → base_footprint` 变换。

→ 因此**路径确实是从 `base_footprint` 出发的，问题在于 `base_footprint` 本身被定位在了
地图原点**。根因是上游 **`map → odom` 定位没有跟踪机器人行驶**（SLAM 认为机器人一直
停在原点），而不是航点跟随 / Nav2 这一层的缺陷。

### 现场确认动作（一步即可定性）

让机器人移动一段，同时观察 `map → base_footprint` 变换是否跟着变：
- **几乎不动、停在原点附近** → 实锤定位未跟踪；进一步查 SLAM 是否真正吃到里程计/雷达、
  是否该用「带已建图 + 初始位姿的定位模式」而非纯建图、地图原点与机器人起点是否对齐。
- **跟着动** → 定位正常，再回到导航层排查。

附带需核对的拓扑隐患：底盘/SLAM 发布的应是 `odom → base_link`（而非 `odom → base_footprint`），
否则 `base_footprint` 会出现两个父节点导致 TF 树冲突。

## 5. 已知边界与待办（按三层归类）

**导航软件层（本报告）**
- **定位（最高优先）**：先解决 `map → base_footprint` 不跟踪的问题，导航才有意义。
- **位置环实车整定**：重载底盘的起停死区、方向参数需按实测微调（既定策略：先按现有
  位置环跑，实车再调）。
- **动态障碍**：当前为静态地图假设，不处理运行中闯入的动态障碍；后续如需，可叠加
  独立的碰撞监控或改造为「监控 + 重规划」。
- **可观测性（建议）**：给航点跟随加诊断护栏 —— 每次规划打印机器人 map 位姿、路径
  起点、目标，并在「路径起点远离机器人 / 机器人长时间不动 / 越界」时报警。

**控制层（治标偏本）**
- **破启前馈**：按需求量给克服静摩擦/万向轮破启的前馈脉冲，是 cm/mrad 级精度的治本
  关键，尚未做。前馈到位后，软件层的死区地板等补偿可显著放松。

**结构层（治本）**
- **菱形轮系改造**：降低底盘非静定（过约束）度，从根上削弱 caster 拖尾与转向阻滞。
  这是让上面两层都变简单、变准的最底层抓手。

## 6. 小结

整件事是**一个物理根因、三层治理**：结构（更大电机/轮径，下一步菱形轮系降非静定）
与控制（STM32 + PI，下一步前馈）从底层治本，导航软件层（位置环 + 航点跟随）叠在其上
做适配。三层是**乘法关系**：底层越静定、前馈越到位，软件层越简单越准。

就软件层而言：航点跟随（规划 → 稀疏化 → 逐段位置环驱动 + 可视化 + 一键启动）已实现并
通过离线验证，代码就绪。实车联调当前卡在**上游定位**（`map → base_footprint` 被钉在
地图原点、不随行驶更新），属定位/TF 层问题，需先在 SLAM/定位侧修复；之后再随结构/控制
改造**同步**推进位置环实车整定与端到端验收，而非靠软件无限堆补偿。
