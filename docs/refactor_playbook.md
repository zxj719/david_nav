# 重构手册：两次重构的教训，以及下一次怎么做

本仓在 2026 年秋天经历了两次大的改动：

1. **9 月的"重构"**：由 AI 自动循环执行，代码和测试在几天内膨胀到原来的数倍。
2. **10 月 W46 的"减法"**：在隔离工作区里有边界地删减，并做了实车验证。

本文把这两次的经过、出过的事故和教训写下来，并给出下一次重构的流程和完成标准。
给 agent 用的操作步骤在 [refactor-task 技能](../.claude/skills/refactor-task/SKILL.md)。

## 0. 名词

| 名词 | 意思 |
|---|---|
| 部署树 | David 上快捷键 20/24/21 实际运行的工作区 `~/ros2_ws_refactor`。它是 symlink-install，**改它的源码会立刻改变现场行为** |
| 隔离工作区 | 为一次改动单独克隆、单独构建的工作区（W46 用的是 `~/ros2_ws_slim`），和部署树互不影响 |
| 变更单 | 写明一次改动的目的、允许改动的范围、必须保留的行为、验收证据和回退点的短文档 |
| WAITING_FIELD | "缺现场证据"状态。到了这一步，执行方必须停下，等现场人员给出结果 |
| 文档形状门禁 | 只检查注释或文档格式、语言的测试，比如"每个函数必须写参数一节""摘要必须是中文"。它不保护任何运行行为 |
| 沙箱 | 在 DDS domain 99 里用假底盘、假定位跑真实 Nav2 图的检查，`colcon test` **不会**自动跑 |

## 2. 事故与教训

### 2.1 最严重：AI 定时循环让测试和文档爆炸

**现象**：执行规程的完成条件是"全部自动任务完成，并连续两轮全量测试全绿"。同时又规定 AI 不能让车动，这一条本身没有错。结果是，实车验收永远处在"等现场"状态，而循环一刻不停，每 4 小时就要找点事做。能自己证明"完成"的只有测试、文档和契约检查，于是工作都堆到了这些地方：

- 测试代码从 3.8 千行涨到约 3 万行（8 倍），其中 27% 只检查注释的格式和语言；
- 改一个纯 docstring 的提交，也要配 SHA 指纹和"非文档部分 AST 等价"的证明；
- 几乎每个功能提交都写着"这不构成实机验收"。

**根因**：当关键证据只能由现场提供时，循环仍然被允许扩大工作范围。复杂度因此堆在**验证成本最低**的地方，而不是**风险最高**的地方。

**以后的做法**：

- 重构**不用定时循环**。一次调用只执行一张已批准的变更单，做完就停。
- 需要现场证据时，写明 `WAITING_FIELD` 并**结束执行**。不允许用补测试、补文档、补抽象来填补等待时间。
- 完成标准写成"哪些现场场景通过了"，不写成测试数量或门禁数量。
- 设一个触发线：一次改动新增的测试行数，如果超过它新增或删除的生产代码行数的 2 倍，就停下来，请人确认。

### 2.2 方案太宽，优先级排反了

**现象**：方案自己列出的约 25 个问题，几乎都是局部问题，例如：

- 驱动没有指令超时；
- 启动脚本会误杀机械臂进程；
- 控制器依赖一个没入库的补丁；
- 两个任务状态机互相抢 Nav2。

每个都是几十到几百行就能修好的。方案却把它们升级成一整套框架：配置编译器、运行记录、离线仿真、体检、金样、多机器人档案、import 规则。只有一台 David，却把"换机器人只改配置"排在第二优先级。

**以后的做法**：从问题清单出发，每个问题做最小的修复。只有出现**第二个真实的使用方**时，才引入通用框架。"将来好扩展""架构更完整"都不算理由。

### 2.3 防御机制会自我繁殖

**现象**：navrun 的生命周期事件先写进本地文件，再投影到 DDS 话题，再由 monitor 收回来去重；为了补发最后一条事件，又加了一个临时进程，配三档超时，还要防止它递归补发自己。实际上**没有任何消费者**从话题上读这些事件。配置编译器用 3.5 千行 Python 去管 800 行 YAML，还出过两次只有编译器才会有的 bug。

**以后的做法**：每个机制都要能写出"谁在用它、它防的是哪次事故"。写不出来就不加，已经有的就删。W46 按这条删掉了事件回流链，没有任何行为倒退。

### 2.4 现场修复没入库，被"简化"覆盖了

**现象**：09-23 现场把避障数据源改成了原始雷达（时延从 1.3 s 降到 0.01 s），但这个修改没有提交。09-24 的一次简化提交把数据源定成了 aligned_scan，**还把测试写成断言"必须读 aligned_scan"**，和现场结论正好相反。

**以后的做法**：现场修复**当天入库**，放在 WIP 分支也可以，提交说明里附上现场数据。编码了现场结论的测试，不能在简化提交里被反转；要反转，必须附上新的现场证据并单独提交。

### 2.5 在部署树上开发，测到的是另一份代码

**现象**：

- 部署树是 symlink-install，在里面改代码，现场快捷键立刻就会跑到未验证的代码。
- 两个沙箱脚本默认加载的是部署树（nav_bringup 用 `REFACTOR_WS` 选工作区，nav_sim 用 `SANDBOX_INSTALL_SETUP`）。不改这两个变量，"测新代码"实际测的是旧代码，而且不会报任何错。

**以后的做法**：所有改动都在隔离工作区里做。跑沙箱之前，先用 `ros2 pkg prefix nav_bringup` 确认路径指向隔离工作区。

### 2.6 测试只在脏树上是绿的

**现象**：

- 09-24 报告"全量 0 失败"。但在干净检出上有 1 个测试必然失败：它扫描的 `launch/` 目录早已删除，只是在部署树里作为被忽略的残留目录还在。
- 沙箱不在 `colcon test` 里。导航启动类的 8 个沙箱检查读的是 09-24 已经删除的配置键，从那天起一直失败，没人发现。
- 假节点没有处理 `ExternalShutdownException`，负载高的时候关停就会失败。
- 后两条已在 2026-10-23 修复（R4-0）：David 上 nav_bringup 沙箱 73/73 通过，nav_sim 的启动和协调检查连跑两轮都通过。

**以后的做法**：

- 基线一律在**干净检出**上建立。
- 每个阶段都要跑沙箱。
- 出现失败时，先在干净的基线构建上复现一遍，再判断是不是"本次改动引起的"。

### 2.7 离线全绿 ≠ 实车可用，测试设计本身也要审

**现象**：第一次实车测试用了 0.5 m 的目标，但到点容差是 0.30 m，车走 0.25 m 就判定成功。测试点离墙只有 0.24–0.40 m，规划器绕路，起步时路径呈锯齿。定位滞后告警按离线估计的 0.6 s 窗口实现，实车上出现了两次误报，后来按现场数据改成了 5 s。

**以后的做法**：

- 目标距离至少是到点容差的 3 倍；
- 测试点四周留出车身尺寸加膨胀半径的空间；
- 每一次试验都逐次记录；
- 阈值类的改动，必须经过一次现场校准才算完成。

### 2.8 外部依赖会在测试之外出问题

**现象**：Lightning 定位开着没关，约 2 小时后发散，位姿漂到了百万米量级。

**以后的做法**：每次测试前都重启定位，并检查位姿是否合理。测试工具要带保护：起点坐标离谱时拒绝发目标。

### 2.9 交接卫生

- **提交作者**：要用真实身份。机器上配的是共享账号，用之前要先改。
- **凭据**：`.bashrc` 里有凭据。读它的时候只 grep 需要的那几行，并且先脱敏。
- **交接文档**：只认一个真源。两份文档各自维护，必然会变得互相矛盾。

## 3. 下一次重构的流程

### 3.1 开始之前

1. **问题清单**：每一条都要写出现象、证据（日志、测量、提交）和影响范围。
2. **现场基线**：在当前部署版本上跑一组固定场景，逐次记录。这组数据是以后比较的标准，**不是**验收标准。如果某个已知缺陷不该保留，要明确标出来，不能当成"必须保持一致"的行为冻结下来。
3. **冻结记录**：记下代码提交、配置和地图的哈希、外部定位版本、快捷键定义。

### 3.2 每一张变更单

| 必填项 | 说明 |
|---|---|
| 类型 | **缺陷修复**（允许改变行为，要说明改正的是哪个错误）或**结构简化**（不得改变已经接受的行为）。两类不能放在同一个提交里 |
| 范围 | 允许改哪些文件，明确不改什么 |
| 必须保留的行为 | 列出对应的回归测试，或者现场场景 |
| 验收证据 | 离线：哪些测试，必须先看到失败再改到通过。现场：哪些场景 |
| 回退点 | 回到哪个提交；配置和地图是否也要一起回退 |

### 3.3 执行

- 在隔离工作区里开发。缺陷修复要**先写一个会失败的测试**。
- 删除时，**测试跟着它所维护的机制一起删**；保护外部行为的测试要迁移，不能删。删除前后各收集一次测试 ID 清单做比对，任何"意外删除"都必须为 0。
- 每个提交的说明要写三件事：删掉了什么，哪些行为不应改变，用什么证据验证。

### 3.4 离线关口

- 干净检出，全量 `colcon build` 和 `colcon test`，0 失败。
- 显式指定隔离工作区跑沙箱。新出现的失败要在干净基线上对照复现，证明是不是本次引起的。

### 3.5 现场关口

- 给现场写一份手把手的手册。参考 W46 第二轮手册的写法：先重启定位并检查健康，选空旷测试点，再跑往返、取消和长时间运行三类测试，最后给出逐次记录表。
- 允许多大的退化，由现场负责人在**比较之前**定下来。

### 3.6 合并与部署

- 只有通过现场关口后，才合并到 `main`，并切换部署。
- 回退靠版本，不靠永久兼容层。

## 4. 不能为了精简而删掉的护栏

| 护栏 | 来自哪次事故 |
|---|---|
| 单实例运行锁，以及跨终端协作停止 | 曾有两套栈同时接管底盘；按进程名强杀误伤过机械臂 |
| 唯一的任务所有者；导航和 Spin 共用一个动作槽 | 两个执行器抢 action client，导致崩溃 |
| 取消屏障；清理失败时保持 busy | 软件层取消了，车还在走 |
| 驱动的指令超时，以及退出时发零速 | 上游崩溃后，车按最后一个速度继续走。**注意**：驱动代码已经实现了超时，但 David 档案里 `chassis.driver.parameters.cmd_timeout_sec` 目前是 `0.0`，也就是**关闭**的（要等实车冒烟测试后再开启），固件也没有失联保护。在开启之前，任何带 SIGKILL 兜底的停止方案（例如 systemd 超时）都不能当作"能物理停车"的保证 |
| 入位容差和到点容差分开；StoppedGoalChecker | 带速度判到达；容差写反 |
| `base_link` / `base_footprint` / POI 采集帧三者区分 | 帧混用导致 0.165 m 偏差、DWB 反复 abort |
| behavior_server 的 frame 和局部代价图一致 | 恢复行为曾经整体失效好几周 |
| 预备点的整车 footprint 校验 | 入位预备点压在障碍上，导致假成功 |
| 定位健康观察（只告警） | 定位发散 28 m 时，导航照样在跑 |

## 5. 完成标准

一次重构算完成，必须同时满足：

1. 问题清单里每一条都有对应的修复，或者有不修的理由；
2. 干净检出全量测试 0 失败，沙箱 0 个新增失败；
3. 现场关口的场景逐条通过，有逐次记录；
4. 改一个导航参数、跨终端停一次车、查一次定位故障，这三件事要经过的步骤都不比改动前多；
5. **没有产生新的通用框架**：没有为了删一个配置编译器又造一套配置语言，也没有为了删一个事件话题又造一条消息总线。

> 保留解决过真实问题的机制，删除为假设中的问题提前建立的框架。缺现场证据时，就停在现场边界。
