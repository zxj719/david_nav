# 2026-05-09 Wheeltec 底盘 IMU 速度死区与通信链路测试报告

## 核心结论

这次最有价值的结论先放在这里：

1. **角速度死区已经比较明确**  
   底盘原地转向的有效启动阈值约在 `0.25 ~ 0.30 rad/s`。  
   `0.30 rad/s` 是刚开始有响应的边界，`0.35 rad/s` 响应明显。后续 Nav2 适配时，建议原地转向最小有效角速度先按 `0.35 rad/s` 配。

2. **线速度死区还不能精确下结论，但已有初步边界**  
   `0.15 m/s` 未观察到可靠运动；`0.20 m/s` 开始有明显加速度扰动；`0.30 m/s` 响应最明确。  
   因为本轮没有 `/odom`，IMU 双积分位移不稳定，所以线速度死区只能先保守认为在 `0.15 ~ 0.30 m/s` 区间内，需要后续用更可靠位移观测复测。

3. **速度指令确实发到了底盘驱动，并写入串口**  
   `/cmd_vel` 非零速度进入了 `wheeltec_robot_node`，并触发 `Stm32_Serial.write()`。  
   测试日志显示每个速度档位都被编码成正确串口帧，例如 `wz=0.350` 对应 `01 5E`，`vx=0.350` 也对应 `01 5E`。

4. **ROS2 上位机代码里没有发现底盘速度死区**  
   `wheeltec_robot_node` 没有 `abs(v) < threshold => 0` 逻辑。  
   当前 `g1_move` 也没有最小速度过滤，只有限幅、`linear.y=0` 和超时停车。  
   实际死区更可能来自下位机固件、电机驱动器或机械静摩擦。

5. **WIT IMU 当前适合判断“是否有明显运动”，不适合单独估计短距离/角度**  
   静止时 `/imu/data_raw` 约 `106 Hz`，加速度模长均值约 `9.770 m/s^2`，标准差约 `0.018 m/s^2`。  
   但 yaw/orientation 在这轮测试里没有可靠反映转角，线速度位移也不能靠 IMU 双积分精确得到。

6. **通信延迟本轮只确认到“上位机驱动收到并写串口”，还没有严格端到端量化**  
   串口写调用在非零速度阶段连续发生，频率约 `1050 Hz`。  
   但由于发布端、驱动回调、IMU 响应没有统一事件 ID，本轮不能严谨给出“发速度后多少秒开始移动”的端到端延迟数值。

## 对后续 Nav2 适配的直接建议

当前 `g1_nav` 里的 Nav2 参数偏低：

- `min_vel_theta: 0.10`
- `min_speed_theta: 0.10`

结合实测结果，这两个值很可能会让 Nav2 发出底盘实际启动不了的低角速度。建议后续先改成：

- `min_vel_theta: 0.35`
- `min_speed_theta: 0.35`

线速度建议先保守处理：

- 不要把 `0.15 m/s` 当成可靠可启动速度。
- 导航初期可先把有效前进速度放在 `0.25 ~ 0.30 m/s` 附近验证。
- 等有可靠位移反馈后，再把线速度最小值往下压。

`velocity_smoother` 当前配置：

- `deadband_velocity: [0.0, 0.0, 0.0]`

这个不会额外压掉小速度，暂时不是主要问题。

## 角速度死区结果

测试方法：

- 直接向 `/cmd_vel` 发布 `linear.x=0`、`angular.z>0`。
- 每档约 1 秒非零角速度，随后发布零速度。
- 只用 `/imu/data_raw.angular_velocity.z` 和加速度扰动判断运动响应。
- 不使用 `/odom`。

| 指令 `angular.z` | IMU `gyro.z` 最大变化 | IMU 加速度模长最大变化 | 判断 |
|---:|---:|---:|---|
| `0.15 rad/s` | `0.0000 rad/s` | `0.056 m/s^2` | 未观察到有效转动 |
| `0.20 rad/s` | `0.0000 rad/s` | `0.059 m/s^2` | 未观察到有效转动 |
| `0.25 rad/s` | `0.0160 rad/s` | `0.042 m/s^2` | 很弱，不作为可靠启动 |
| `0.30 rad/s` | `0.0714 rad/s` | `0.102 m/s^2` | 开始有明确响应 |
| `0.35 rad/s` | `0.2929 rad/s` | `0.109 m/s^2` | 响应明显 |

结论：

- 角速度死区约 `0.25 ~ 0.30 rad/s`。
- 建议最小有效原地转向速度使用 `0.35 rad/s`。
- 当前 IMU yaw/orientation 不可靠，所以本轮没有给出角度误差。

## 线速度初步结果

测试方法：

- 直接向 `/cmd_vel` 发布 `angular.z=0`、`linear.x>0`。
- 用 IMU 加速度响应和粗略积分估计运动。
- 不使用 `/odom`。
- 用户现场确认 USB 重插后底盘发生了实际移动。

| 指令 `linear.x` | IMU 粗略位移估计 | 加速度最大变化 | 角速度最大变化 | 判断 |
|---:|---:|---:|---:|---|
| `0.15 m/s` | `0.000 m` | `0.065 m/s^2` | `0.0000 rad/s` | 未观察到可靠运动 |
| `0.20 m/s` | `-0.000 m` | `0.941 m/s^2` | `0.0309 rad/s` | 有明显加速度扰动 |
| `0.25 m/s` | `0.004 m` | `0.241 m/s^2` | `0.0927 rad/s` | 有响应，但位移估计不稳定 |
| `0.30 m/s` | `0.082 m` | `1.057 m/s^2` | `0.3324 rad/s` | 明显运动 |
| `0.35 m/s` | `0.002 m` | `0.381 m/s^2` | `0.0415 rad/s` | 有响应，但积分位移不可信 |

结论：

- 线速度指令确实能到达底盘，部分档位产生实际运动。
- IMU 双积分短距离位移不可信，不能把表中的位移当成精确距离。
- 初步看 `0.20 m/s` 开始有响应，`0.30 m/s` 最明确。

## 代码与参数线索

### 底盘驱动

`wheeltec_robot_node` 的 `/cmd_vel` 回调只做编码发送：

- `linear.x * 1000`
- `linear.y * 1000`
- `angular.z * 1000`

没有发现：

- `abs(vx) < 某值` 后置零
- `abs(wz) < 某值` 后置零
- 最小速度补偿

### `g1_move`

当前 `g1_move` 只做：

- `linear.x` 最大限幅
- `angular.z` 最大限幅
- `linear.y = 0`
- 超时后发布零速度

没有最小速度死区。

### 参数文件

旧 Wheeltec DWA 参数中有：

- `min_vel_trans: 0.1`
- `min_vel_theta: 0.3`

当前 `g1_nav` Nav2 参数中有：

- `min_vel_theta: 0.10`
- `min_speed_theta: 0.10`
- `deadband_velocity: [0.0, 0.0, 0.0]`

判断：

- 旧 Wheeltec 的 `min_vel_theta: 0.3` 与本轮实测角速度死区吻合。
- 当前 `g1_nav` 的 `0.10 rad/s` 对这个底盘偏低。

## 通信延迟状态

本轮已经确认：

- 发布非零 `/cmd_vel` 后，`wheeltec_robot_node` 能收到并写串口。
- 非零速度阶段串口写调用连续存在。
- 没有发现上位机层面丢弃小速度。

本轮尚未严格量化：

- 发布端时间戳到 `wheeltec_robot_node` 回调时间戳的延迟。
- 串口写出到下位机执行的延迟。
- 下位机执行到 IMU 首次检测运动的延迟。

原因：

- 测试脚本和驱动日志没有统一事件 ID。
- 串口日志时间戳来自 ROS 日志，IMU 响应时间来自测试脚本本地循环，两者没有做严格配对。

下一步应该补一个专用 latency probe，记录：

- `t_publish_cmd`
- `t_cmd_echo_seen`
- `t_driver_callback`
- `t_first_imu_accel_or_gyro_response`
